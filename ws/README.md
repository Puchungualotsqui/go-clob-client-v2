# CLOB WebSocket

This package uses `github.com/gorilla/websocket`, included in the parent module.

`NewClient` accepts a base endpoint (empty selects the production endpoint). Streams created by the same client share one market connection, and one user connection per distinct set of credentials. Connections retry failures, replay active subscriptions after reconnecting, and use text `PING`/`PONG` heartbeats. Valid U256 asset IDs are sent and matched as decimal strings; valid B256 market IDs are sent and matched as lowercase `0x`-prefixed hex strings. Equivalent representations share a subscription. Other nonempty string IDs remain unchanged and match exactly for compatibility. Wire asset IDs may also be unsigned JSON integers up to `uint64`; wire market IDs may also be arrays of 32 bytes. Malformed non-string IDs are reported on `Errors` and the event is not delivered to that stream. In a syntactically valid batch, malformed event headers are reported without suppressing the other events; malformed routing IDs reject only their own event. Invalid JSON rejects the entire frame. `ParseMessages` likewise returns valid batch messages alongside an error for malformed elements, so callers can inspect both results. An empty user market list subscribes to all markets.

IDs are reference-counted per connection (including duplicate IDs in a single call): closing or canceling a stream releases only its interests. When the last reference to an ID is released, an unsubscribe is sent if connected (unless a wildcard user subscription covers it). Released IDs are remembered for the lifetime of that connection. Reusing one forces a reconnect before adding it to the wire subscription, so frames in flight on the retired connection cannot reach its replacement subscriber. To bound this history, releasing 4096 distinct IDs on one connection also forces a reconnect. The last stream closes the shared connection. `Close` is safe to call concurrently; cancellation also releases the stream, but neither operation guarantees the server received an unsubscribe if the connection fails. Market events are routed by asset ID, including IDs in price-change batches and market lifecycle events. Like Rust, a `price_change` event is delivered **whole** if any entry matches: a batch can contain entries for assets the recipient did not subscribe to, so filter entries when applying updates. User events are routed by their `market` field; a user event without a market is delivered only to wildcard streams. Each recipient owns its `Raw` bytes.

Wildcard user streams share the connection with explicit-market streams. Entering wildcard mode while explicit markets are active, or leaving it while explicit streams remain, reconnects and replays the desired subscription. This avoids relying on an empty unsubscribe having a particular server-side meaning. Such transitions can interrupt delivery. Different credentials never share a connection, even when their API keys match.

```go
client, err := ws.NewClient("", ws.Config{})
if err != nil { /* handle error */ }
stream, err := client.SubscribeMarket(ctx, []string{"123"}, true)
if err != nil { /* handle error */ }
defer stream.Close()
for msg := range stream.Messages {
    // msg.EventType identifies the event; msg.Raw preserves the entire JSON.
    // msg.ConnectionID, msg.Generation and msg.ReceivedAt describe its delivery.
    // msg.Decode(&event) decodes it into an application-specific struct.
    // msg.Typed() returns a pointer to the matching package event type.
    // msg.Midpoint() computes the exact midpoint for book events.
}
```

Import this package as `github.com/puchungualotsqui/go-clob-client-v2/ws`; the example assumes `ctx` is a `context.Context`. Drain `Messages` promptly: a full buffer stops only that stream and reports an error rather than silently dropping data. `Errors` is a bounded diagnostic channel; both channels close when the stream ends. A production consumer should monitor both channels. Routine diagnostics are best-effort. Important lifecycle errors take priority over older queued diagnostics when the buffer is full; callers must still drain `Errors` because later lifecycle errors can replace earlier ones. Connection and parse errors may be reported to multiple streams. Active streams receive `ws.ErrReconnecting` when ID reuse, retirement-history limits, a wildcard transition, a custom-feature upgrade, or a subscription write concurrent with an overflow unsubscribe intentionally replaces a connection; use `errors.Is` and reconcile state. Network and write failures are also reported, but do not imply a successful replay. `MaxAttempts` limits consecutive failed connection attempts (zero means unlimited); successful connections reset the counter. Exhausting retries closes all streams on that connection with an error matching `ws.ErrRetriesExhausted`. Retry delay doubles up to `MaxBackoff`.

### Delivered-message metadata and read limits

Each stream-delivered `Message` has a `ConnectionID` identifying its physical WebSocket connection across all clients and groups in this process, a `Generation` matching that group's successful full subscription write, and `ReceivedAt`, captured with `time.Now()` immediately after the complete WebSocket message has been read and decompressed, before JSON parsing, routing, or channel delivery. IDs are assigned when a successful handshake is installed in a live group, including those whose subscription write fails, so values may have gaps; they are process-local, reset on process restart, and are unique and nonzero only until the uint64 counter wraps. Different subscribers receiving the same event get the same metadata and independent `Raw` bytes. Events from the same JSON batch share the timestamp, ID, and generation. The timestamp is local read-completion time, not server event time, first-byte arrival, or consumer delivery time; scheduling, buffering, fragmentation, decompression, and clock adjustments affect it. `ParseMessages` and manually constructed messages have zero metadata unless set by the caller. Metadata is excluded when marshaling a `Message` as JSON; `Raw` and `Decode` are unchanged.

`ConnectionID` distinguishes sockets even when group generations reset after the last stream closes, or across different clients and channels. `Generation` is group-scoped and agrees with `StreamState.Generation` for that connection, but a later call to `State()` can already reflect a different connection. Buffered messages can be consumed after a reconnect, and lifecycle notifications and messages have no cross-channel ordering. Neither an unchanged connection ID nor a new one proves continuity, completeness, server acceptance, or recovery; use application-specific reconciliation.

`Config.ReadLimit` sets the maximum inbound WebSocket **message** size in bytes (not per frame), including text, binary, and PONG text messages. Zero or negative selects `DefaultReadLimit` (16 MiB); choose a larger positive value for larger snapshots. The limit applies to payload bytes rather than WebSocket framing overhead, and is enforced both on the compressed wire payload and on the decompressed payload when compression is negotiated. On an oversized message, the connection is closed with WebSocket close code 1009, active streams receive an error wrapping `websocket.ErrReadLimit` on their best-effort `Errors` channels, and normal reconnect/replay follows; the oversized message is not delivered. This limit bounds each payload, not total process memory or JSON parsing and fan-out allocations. `ParseMessages` does not apply it. Oversized messages may recur after reconnect, and replay does not guarantee gap recovery.

Adding fields to exported `Message`, `Config`, and `StreamState` preserves ordinary keyed literals and existing methods but Go unkeyed struct literals must be updated.

### Opt-in strict market validation

Set `Config{StrictMarket: true}` when creating a client to apply strict validation to its **shared market connection** and all market streams using it. The default remains permissive, and user connections and `ParseMessages` are unaffected. For each complete market text message other than the text heartbeat `PONG`, strict mode validates the entire JSON object or array before routing any event. It rejects invalid UTF-8, invalid JSON or event headers, missing or empty `event_type`, unknown market event types, and routing data that the market router cannot parse. Outside JSON strings, only JSON whitespace (space, tab, carriage return, and line feed) is accepted. Every event must have at least one nonempty asset routing ID in `asset_id`, `asset_ids`, `assets_ids`, or a `price_changes` entry; provided IDs must be parseable by the existing routing rules, list entries cannot be null, and every `price_changes` entry must have a nonempty `asset_id`. Missing or null optional routing fields are ignored. Opaque nonempty string IDs retain the existing exact-match behavior. A valid event for an ID no current stream subscribes to is not an error; it is filtered normally. An empty JSON array is accepted. Binary market messages are rejected; WebSocket control frames are handled by the underlying library.

Before decoding or routing, strict mode also examines every JSON object recursively, including objects in arrays and unknown extension fields. It rejects empty or control-character object keys; duplicate keys and keys equal under Unicode simple case folding within the same object (including escaped spellings); and noncanonical case variants of known market protocol keys at any depth, even if no canonical spelling is present. The recognized names are `event_type`, `asset_id`, `asset_ids`, `assets_ids`, `price_changes`, `id`, `market`, `timestamp`, `price`, `size`, `side`, `hash`, `bids`, `asks`, `best_bid`, `best_ask`, `spread`, `old_tick_size`, `new_tick_size`, `fee_rate_bps`, `question`, `slug`, `description`, `outcomes`, `event_message`, `ticker`, `title`, `winning_asset_id`, and `winning_outcome`. It rejects invalid UTF-8 anywhere in the message and unpaired UTF-16 surrogate escapes in keys or values, rather than accepting the decoder's replacement character. Valid escaped keys and paired surrogates are accepted. Unknown nonempty keys remain allowed, including mixed-case keys that do not collide or case-fold to a reserved name; this is not a full schema check. These stricter checks can reject messages previously accepted in strict mode; the default permissive mode is unchanged.

On rejection, **no event from that message is delivered**. If its connection is still current, it is retired, the group's `Interruptions` and `StrictMarketRejections` counters advance together in `State()`, and normal reconnect/replay follows. `ErrStrictMarketMessage` is reported on each active market stream's bounded `Errors` channel as a critical diagnostic, but it can still be displaced by later errors. Use `State().StrictMarketRejections` rather than `Errors` to detect strict rejections, and treat `StateChanges` only as a coalesced wakeup. The counter survives later replays and stream closure, is shared by the group, and resets when a new group is created after the last stream closes; a joining stream sees the group's current count. A frame from a connection already retired while validation was in progress is discarded without attributing a rejection to the replacement. Read-limit, transport, and other non-validation interruptions advance `Interruptions` but not this counter. Counters are uint64 and can wrap.

Strict mode validates framing, event headers, supported event types, and the routing fields described above, **not the complete event schema or business semantics**. For example, other malformed or absent event fields may still be delivered; `Message.Typed()` performs additional checks only when the caller invokes it. It does not detect server-side omissions, stale or reordered events, duplicates, missing snapshots, or other gaps. Previously buffered messages are not cleared when a connection is retired, and normal per-stream buffer overflow can terminate a slow stream. Reconnects can repeatedly reject a server's new event type until the client supports it or strict mode is disabled. As with ordinary reconnects, reconcile application state; strict mode does not establish continuity or gap-free recovery.

### Recovery state

Use `stream.State()` as the authoritative **local, current** lifecycle snapshot and `stream.StateChanges` as a coalescing wakeup. `StreamState` has a per-stream `Version`, a group `Generation` (successful full subscription writes), a group `Interruptions` count (retired connections while subscribers remained), and a `Phase`:

- `PhaseConnecting`: no connection has yet been retired or successfully subscribed for this group.
- `PhaseReplaySent`: the current connection's full subscription request was written. This includes the initial connection; streams joining an active connection see the current group state.
- `PhaseInterrupted`: a connection was retired and no replacement full subscription has been written yet. `Generation` is the last successful write and `Interruptions` has advanced.
- `PhaseClosed`: this stream is no longer valid for delivery; its final snapshot remains available. On buffer overflow, the phase and version change atomically with the failed send, before group unlock or unsubscribe I/O. The snapshot records the group counters at that point, even if cleanup later causes another group transition.

Each state transition advances `Version`; a failed dial without an established connection does not by itself change the phase or counters (dial errors are reported on `Errors`). On reconnect, `PhaseReplaySent` has a new `Generation` and retains the interruption count, correlating the replay with the latest observed interruption. The counter also exposes interruptions that happened while wakeups were coalesced. Counters belong to the shared group and reset when its last stream closes and a new group is created. A stream that joins a group sees its current counters, not necessarily zero.

`StateChanges` has one buffered wakeup, not an event log. After each receive, read `State()`; if several transitions occurred, the snapshot is the latest. It is safe to call `State()` concurrently, but only one consumer should drain `StateChanges` (fan out notifications if needed). On overflow it closes when the state is invalidated, before unsubscribe I/O. `Messages`, `Errors`, and `Replays` close after local removal and may contain buffered values; `Close()` waits for those channels, not for the overflow unsubscribe write. A buffered state wakeup may still be read after closure. For example:

```go
for range stream.StateChanges {
    state := stream.State()
    if state.Phase == ws.PhaseReplaySent {
        // Reconcile using state.Generation and state.Interruptions.
        // Recheck State after asynchronous work; Version detects transitions.
    }
}
```

This snapshot describes what the client has observed, not an atomic barrier against future failures: a connection may already be broken before the read loop detects it, and it can fail immediately after any state check. A successful write is **not** a server acknowledgment, a snapshot-complete signal, or proof that missed events were recovered. Rechecking `Version` can detect observed transitions during reconciliation, but cannot make external work atomic with connection state.

`Stream.Replays` remains available for compatibility: it reports full writes with a generation and `Reconnected` flag, coalescing unread notifications to the latest replay. Joining an already-connected group or sending an incremental subscription does not produce one. **Do not use `Replays` and `Errors` as an ordered lifecycle:** an unread replay from an earlier connection can be received after an interruption, and an older error can be received after a newer replay. Notifications and messages on different channels have no cross-channel ordering; use `State()` for recovery decisions.

`Message.Typed` supports book, price change, tick size change, last trade price, best bid/ask, new market, market resolved, user trade, and user order events. Decimal values and timestamps use `json.Number` to preserve precision; IDs and enum-like fields are strings. Optional scalar fields are pointers. Typed decoding checks required fields, identifier formats, and quoted i64 timestamps, but does not enforce Rust's decimal range or enum validation. `Decode` remains permissive and `Raw` retains the original JSON; a routed opaque ID need not be accepted by `Typed`. Unknown event types return an error from `Typed`; their raw JSON remains available from `ParseMessages`. Stream parsers currently filter unknown event types.

Subscription requests and reconnect replays request `initial_dump: true`. As in Rust's ID multiplexing, a stream joining an already subscribed ID does **not** receive a separate initial dump; it receives subsequent events. A new subscriber can also observe a dump requested for another stream. Applications requiring an independent snapshot should obtain one separately. A stream joining an ID that remains active can also receive an in-flight event read before it joined; there are no per-subscriber sequence markers. The retirement policy rejects frames from the old connection, not historical data the server may send on the new one. There is no protocol acknowledgement or sequence-based recovery here, so reconnects, wildcard transitions, and network failures can leave gaps; reconcile state after reconnects.

Overflowed streams are removed locally and their unsubscribe writes are serialized asynchronously, so healthy streams on the same connection can continue reading while a write is blocked. Released IDs are recorded before that write; reuse still forces a reconnect. If a subscription change needs a write while an overflow unsubscribe is pending, the client replaces the connection and replays the desired subscriptions instead of blocking on the write; the change may interrupt healthy streams, and a concurrent `Close()` can return `ErrReconnecting`. A failed asynchronous write also retires the current connection and is reported to remaining streams. If the last stream overflows, its group is unpublished immediately, but closing its old physical connection can wait for the unsubscribe write or its deadline. As with other writes, delivery and server-side unsubscribe are not guaranteed across failures. This nonblocking path is specific to overflow cleanup; ordinary subscription, explicit close, and heartbeat writes still run under the group lock and can delay that group's delivery until the write completes or fails.

Custom features are enabled for the shared market connection if any stream requests them. Enabling them after another market stream is active reconnects and replays all active IDs with the flag set; the flag stays enabled until the last market stream closes. Consequently streams that requested `false` can also receive custom event types. Unlike Rust's lagging broadcast receivers, a slow Go stream is terminated instead of silently skipping messages.

Credentials are included in user subscription and unsubscribe messages. Use `wss://` for real credentials and do not log the serialized requests. Multiplexing and replay assume the server treats subscriptions as sets of IDs and honors wildcard subscriptions on a fresh connection; the protocol provides no acknowledgement to verify those assumptions.
